# Design

## Context

- `package.sh` builds the DMG at the end of packaging (`package.sh:338`): it stages `Clair.app` and an `/Applications` symlink, runs `hdiutil create -fs HFS+ -format ULFO` with up to three attempts (it fails now and then on hosted runners), then signs, notarizes and staples the DMG.
- `package.sh` runs in three places: `release.yml`'s `package` job on the owner's Mac; `tests/runtime/run.sh` on hosted `xcode-27` runners, which builds a DMG for the update test; and `package.test.sh` in `ci.yml`, which builds one with real `hdiutil` and checks its contents.
- `package.sh` gets Sparkle the same way every time: `scripts/fetch-sparkle.sh` downloads a pinned, checksummed tarball into `build/sparkle`, unless `--sparkle` names a directory.
- The artwork lives in `resources/icon/`. SVGs are generated by Python scripts, then rendered to PNGs with `rsvg-convert` by `scripts/render-icon-images.sh`, and the renders are committed. `ci.yml` already installs `librsvg`.
- The packaged app's icon is `Contents/Resources/app.icns` (`CFBundleIconFile`), compiled into the engine from `resources/icon/AppIcon.icon`.
- Finder stores a window's layout in the volume's `.DS_Store`: size, view options, icon positions and the background image (an alias to a file on the volume). It draws icon labels in black in Light Mode and white in Dark Mode, and never changes a DMG's background with the appearance.

## Goals / Non-Goals

**Goals:**
- The layout is described in a committed settings file and reproduced exactly on every run, with no GUI session, Finder scripting or Automation permission.
- Packaging stays one command (`package.sh`). The new tool is pinned and verified like Sparkle.
- The layout is checked automatically on every pull request, and by eye once per release.

**Non-Goals:**
- Showing layout or background changes in a pull request without a package. The renders are committed, so a pull request shows the PNGs.
- Making the background follow the appearance. Finder can't.

## Decisions

### D1. `dmgbuild` builds the DMG

`dmgbuild` (MIT, Python 3.10 or later, version 1.6.7 at the time of writing) writes the `.DS_Store` itself with its `ds_store` and `mac_alias` libraries, then runs `hdiutil` to create and convert the image. A settings file sets the volume name, format, filesystem, window size, icon size, icon positions, background, volume icon and hidden UI. Its optional badge-icon support needs PyObjC, which isn't used.

**Alternatives considered:**
- sindresorhus `create-dmg` (Node): it also writes `.DS_Store` directly, through `appdmg`, and looks good without configuration. But its layout is fixed, it names the file itself, it signs by default (we'd pass `--no-code-sign`), and it adds Node to the owner's Mac and the hosted jobs.
- `create-dmg/create-dmg` (shell): scripts Finder through AppleScript, so it needs a logged-in session and Automation permission, and it's known to be flaky in CI.
- Chromium's `pkg-dmg`, as Chrome and ungoogled-chromium-macos use: it copies a `.DS_Store` made by hand in Finder. That file is opaque in review and has to be remade by hand for any layout change.
- Writing the `.DS_Store` with `ds_store` directly: that's most of what `dmgbuild` already does, without its tests.

### D2. `scripts/fetch-dmgbuild.sh` installs it, as `fetch-sparkle.sh` installs Sparkle

The script creates a virtual environment in `build/dmgbuild/` from `resources/dmg/requirements.txt`, which pins `dmgbuild`, `ds_store` and `mac_alias` with their hashes (`pip install --require-hashes --no-deps --only-binary :all:`). It reuses an environment whose recorded requirements match, and prints the path to the `dmgbuild` executable. `package.sh` runs it unless `--dmgbuild <path>` names one. The script needs a Python of 3.10 or later: the owner's Mac has Homebrew's 3.13, and the hosted `xcode-27` image has its own. The script gets a `*.test.sh` with a stand-in `pip`.

Hash-pinning matters because `package.sh` runs in the `release` environment, next to the signing keychain.

**Alternatives considered:** installing `dmgbuild` in each workflow step. That would spread the pin across three workflows and leave local packaging on whatever version happens to be installed.

### D3. Layout and artwork in `resources/dmg/`

- `layout.json`: the window's position and size, the icon and label sizes, and the two icon positions, read by both `settings.py` and `make_background.py`. The window is 660 × 400 points with 128-point icons. Clair is at (180, 200) and Applications at (480, 200).
- `settings.py`: the `dmgbuild` settings: the layout from `layout.json`, with the toolbar, sidebar, status bar and path bar off. The format stays `ULFO` on HFS+. It doesn't use `dmgbuild`'s `hide_extensions`: that sets Finder info on the app bundle, which makes `codesign --verify --strict` fail on the DMG's copy of the app. Finder already labels an app without its `.app`.
- `background.svg`: the 660 × 400 artwork, written by `make_background.py` from the same geometry as `resources/icon/make_layers.py`, so the ring and the colours match the app icon. It has a curved arrow between the two icon positions, read from `layout.json`. The tone keeps black and white labels both readable: a mid-tone field, or a lighter plate under each label, picked by checking both appearances.
- `background.tiff`: the committed render, which `dmgbuild` copies to `.background.tiff` at the volume's root. `scripts/render-dmg-background.sh` renders the SVG at 660 × 400 and 1320 × 800 with `rsvg-convert`, then joins them with `tiffutil -cathidpicheck`. That gives Finder one file with both resolutions, which it picks between for the display. `package.sh` needs only the TIFF, so packaging doesn't need `rsvg-convert`.
- The volume icon is the packaged app's own `Contents/Resources/app.icns`, read from the app being packaged, so it can't drift from the app icon.

`settings.py` reads the paths it needs (app, volume icon, background) from `dmgbuild`'s `-D` definitions, which `package.sh` passes. It holds no absolute paths.

### D4. `package.sh` swaps `hdiutil create` for `dmgbuild`

The staging folder and `ditto` copy go, since `dmgbuild` copies the app and makes the symlink itself. The three-attempt loop stays around the `dmgbuild` call, now with 30 seconds between attempts. On hosted runners, for about a minute after a job's first `xcodebuild`, `simdiskimaged` keeps retrying an unmount of a simulator runtime by its disk number. A DMG attached in that window can reuse the number and be unmounted while `dmgbuild` writes to it. This is most likely what made `hdiutil create` fail now and then before. `quality.yml` hits it, since `run.sh prepare` builds ClairUI just before packaging; the 30-second waits outlast the window. Signing, notarization and stapling after it don't change. The output name stays `Clair-<version>-arm64.dmg`.

### D5. How the layout is checked

- **`package.test.sh` (every pull request):** it mounts the DMG it builds and checks these:
  - `Clair.app` and the `Applications` symlink are the only visible items
  - `.background.tiff` holds two images, at 660 × 400 and 1320 × 800 (`tiffutil -info`)
  - `.VolumeIcon.icns` matches the app's `app.icns`, and the volume root has the custom-icon Finder flag
  - the `.DS_Store`, read with the `ds_store` library from the `dmgbuild` environment, gives each item the position in `layout.json`, and sets the window size, icon size, the bars off and a background alias to `/.background.tiff`
- **The runtime suite:** its update test already installs an update from a DMG `package.sh` built, which now has the layout. It gains a check that the update replaced only `Clair.app` and left nothing else beside it.
- **The release checklist (by eye):** `docs/releasing.md` gains an item to open the dry-run DMG in Light and Dark Mode and on a Retina and a standard display, if both are at hand.

## Risks / Trade-offs

- **[Risk] Finder ignores or misreads the `.DS_Store` on a new macOS version.** → `dmgbuild` writes the documented, long-stable format, and the checklist's look by eye would catch it. The fallback is a plain DMG, which still installs.
- **[Risk] Labels are unreadable in one appearance.** → D3's tone rule, and the checklist checks both appearances.
- **[Risk] A supply-chain change in `dmgbuild` or its dependencies.** → Hash-pinned wheels, no dependency resolution at install (`--no-deps`), and upgrades only through a reviewed change to `requirements.txt`.
- **[Risk] Sparkle copies more than `Clair.app` from the DMG.** → Sparkle looks for the app bundle with the host's bundle ID and installs only that, so the layout files stay on the volume. The runtime suite's update test confirms it.
- **[Trade-off] Committed renders can drift from their SVG.** → The render script's test re-renders and compares sizes, and the README says to commit both together, as for the logos.
- **[Trade-off] Python on the release path.** → It was already needed for the engine build on the same Mac, and the environment is per checkout and pinned.

## Migration Plan

1. Land the artwork, settings, `fetch-dmgbuild.sh` and the `package.sh` change in one pull request, with the tests.
2. Run a release dry run, then check the DMG by eye in both appearances.
3. The next release ships the new window. Earlier DMGs on GitHub Releases stay as they are, and deltas don't involve the DMG layout.

Rollback: revert the pull request. `package.sh` goes back to `hdiutil create`, and nothing else depends on the layout.
